When new information supersedes something already written in a memory file, rewrite the affected passage as a clean statement of current understanding. Don't layer on "X was the old view, then corrected to Y on [date]" narrative.

**Why:** The user pushed back on this directly (2026-07-28) when I kept a rejected analogy ("Unity-style") in a memory file as a contrast marker after they'd corrected it. Memory files are supposed to be organized semantically, not chronologically — a discarded intermediate hypothesis is noise once superseded, even when it's being used to encode a "don't do this" signal.

**How to apply:** If there's a genuine reason to preserve the negative space (an approach that was explicitly ruled out and might otherwise get re-proposed), capture the *constraint* it implies in plain terms, not the name of the rejected idea or the fact that a correction happened. E.g. instead of "not a Unity-style rendering engine (that was the original framing, corrected 2026-07-28)," just state the actual constraint: "judged by whether it gives clean extension points, not by whether it renders identically everywhere." Applies to all memory edits, not just project-type ones.
